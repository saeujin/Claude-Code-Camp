# 식단 관리 웹앱 — 구현 계획

## Context

`식단앱 기능 명세서`(F1~F6)를 구현한다. 그린필드이며, 사용자가 정한 7단계 순서를 따른다.

이 앱의 구조적 핵심은 명세서 §2에 있다. **F1이 세운 목표 칼로리가 기준선이고, F4·F5·F6은 전부 그 기준선과의 차이(잔여 칼로리)를 입력으로 받는다.** 따라서 추천 기능은 독립 모듈이 아니라 F1에 종속된 계산이다. 구현 순서도 이 의존성을 따라야 한다.

### 7단계 ↔ 기능 매핑

| 단계 | 내용 | 대응 기능 |
|---|---|---|
| 1 | 식약처 데이터 수집 및 재료명 정리 | F5 (레시피), **F2·F4 (음식 영양 DB)**, **AI 재료 정규화** |
| 2 | 냉장고·식사 기록·사용자 설정 데이터 구성 | F1, F2, F3 |
| 3 | 추천 점수와 제외 조건 구현 | F1 계산, F4, F5 |
| 4 | 추천 결과 정상 여부 테스트 | F1·F4·F5 |
| 5 | 모바일 웹 화면 제작 | F1~F6 전체 |
| 6 | 레시피 공유 링크 | (명세 외 추가 요구) |
| 7 | 사진 인식 / 자연스러운 추천 설명에 AI 추가 | F3 사진, F4·F5 설명문 |

> **AI 사용 위치가 1단계로 앞당겨졌다.** 재료명 정규화("칵테일새우 → 새우", "달걀 ↔ 계란")는 규칙과 수작업 사전으로는 풀리지 않아 LLM이 필요하다. 자세한 근거는 1-c. 7단계의 AI(사진 인식·설명문 자연화)는 그대로 선택 사항으로 남는다.

**1단계가 원래 계획보다 커졌다.** 명세서 F2·F4는 레시피가 아니라 **개별 음식**(닭가슴살 샐러드, 계란 2개)의 칼로리를 요구한다. 레시피 DB로는 이걸 못 채운다. 서로 다른 데이터셋 두 벌이 필요하다.

### 명세서에서 정리가 필요한 두 지점

**(a) F4 "남은 끼니 수" 정의가 §F4 본문과 S3에서 어긋난다.**
§F4는 *"점심 시점에 저녁·간식이 남았다면 두 끼로 나눔"*(=2), S3는 *"1,713을 점심·저녁·간식 세 끼로 균등 배분 → 571"*(=3)이다.
→ **S3 쪽을 채택한다**: `남은 끼니 = 추천 대상 끼니를 포함해, 오늘 아직 기록이 없는 끼니의 수`. 간식은 항상 후보에 포함. 1,713 ÷ 3 = 571로 S3의 숫자가 재현된다.

**(b) 알레르기·기피 재료가 명세에 없다.**
음식을 추천하는 앱에서 이건 안전 문제다. 점수를 낮추는 방식으로는 언젠가 추천되므로, **하드 필터(후보에서 배제)** 로 넣어야 한다. 다만 명세 범위 밖이므로 **F1 프로필에 선택 입력 필드 하나 + F4·F5 배제 로직**이라는 최소 형태로만 3단계에 포함한다. 원치 않으시면 빼겠습니다.

### 1단계 — 데이터 수집 및 재료명 정리 ★ 최대 리스크

여기가 실패하면 뒤가 전부 무의미하다. **끝내고 결과를 눈으로 확인한 뒤** 2단계로 간다.

**1-a. 레시피 수집** — `scripts/fetch-recipes.ts`
1,000행씩 호출해 전량 수신 → `data/raw-recipes.json`. 1회성이며 앱 런타임에는 절대 호출하지 않는다.

**1-b. 음식 영양 수집** — `scripts/fetch-nutrients.ts`
9.2만 건 수신 → `data/raw-foods.json`. 식품분류 기준으로 원재료성/가공식품 구분 플래그를 함께 저장(F2 검색 정렬용).

**1-c. 재료명 정규화** — `scripts/normalize-ingredients.ts` ← **AI를 쓰는 곳 (1)**

`RCP_PARTS_DTLS`는 자유 텍스트다:
```
두부 75g, 칵테일새우 20g(5마리), 달걀 50g(1개), 대파 1/2대, 소금 약간
```

**왜 규칙 기반과 수작업 사전으로는 안 되는가.** 실패가 두 종류다:

| 유형 | 예 | 문자열 매칭 결과 |
|---|---|---|
| 수식어가 붙은 하위 표현 | 칵테일새우 / 냉동새우 / 흰다리새우 → **새우** | 부분 문자열은 걸리지만, 어디를 잘라야 할지는 규칙으로 못 정한다 (`대파` ⊂ `파`는 맞지만 `파프리카` ⊂ `파`는 틀림) |
| 글자가 아예 다른 동의어 | 달걀 ↔ 계란, 부추 ↔ 정구지, 물오징어 ↔ 오징어 | 부분 문자열 0% — 사전에 없으면 영원히 못 찾는다 |

두 번째 유형은 손으로 다 채울 방법이 없다. **LLM으로 정규화한다.**

**핵심 설계 — 레시피 1,100건이 아니라 "고유 재료명 목록"을 정규화한다.**

```
① 정규식 파싱      RCP_PARTS_DTLS → { 원문이름, 수량, 단위 }
                    75g / 1/2대 / 1개 / 약간(수량 null) 패턴 처리
                    → 총 약 11,000개 항목, 고유 원문이름 약 1,500~2,500개

② LLM 정규화       고유 이름만 100개씩 묶어 처리 (약 20~25회 호출)
                    이미 확정된 정규 어휘 목록을 프롬프트에 함께 넣어
                    새 이름을 기존 어휘에 붙이거나, 없으면 새 어휘를 만든다
                    → data/ingredient-map.json  (원문 → 정규명 + 카테고리)

③ 결정적 적용      ②의 매핑표를 11,000개 항목에 그대로 적용
                    → data/recipes.normalized.json
```

②의 출력 스키마 (Zod → `zodOutputFormat` → `client.messages.parse()`):

```ts
{ raw: "칵테일새우", canonical: "새우",   category: "해산물", isStaple: false }
{ raw: "달걀",       canonical: "계란",   category: "육류·알", isStaple: false }
{ raw: "다진 마늘",  canonical: "마늘",   category: "채소",   isStaple: true  }
{ raw: "국간장",     canonical: "간장",   category: "양념",   isStaple: true  }
```

- **`category`는 상위 카테고리가 아니라 "대체 가능 그룹"이다.** 닭가슴살·닭다리살은 각자 `canonical`을 갖되 같은 `category: "닭고기"`를 공유한다. 레시피가 닭고기를 요구하고 냉장고에 닭가슴살만 있을 때 F5가 이걸 매칭시키는 근거가 된다 (완전 일치 1.0, 카테고리 일치 0.7).
- **`isStaple`도 LLM이 판정한다.** 소금·후추·간장·설탕·식용유 등 항상 있다고 가정할 양념 (명세서 F5 제약사항). 규칙으로는 "국간장/진간장/양조간장"을 다 못 잡는다.
- **프롬프트 캐싱**: 누적 정규 어휘 목록을 매 호출에 넣으므로 `cache_control: {type:"ephemeral"}`로 캐시한다 (opus-5 최소 512토큰 — 충족).
- 모델 `claude-opus-5`, `effort: "medium"` (1회성 배치이므로 품질 우선).

**비용**: 고유 이름 2,000개 기준 20여 회 호출, 입력 누적 약 60k · 출력 약 40k 토큰 → **1회 2~3달러**. 이후 결과는 `data/` 에 커밋되므로 **런타임 LLM 호출 0회, 매번 동일한 결과.**

**검수 산출물**: `data/normalization-report.md` — 정규명별로 묶인 원문 목록을 빈도순으로 출력. 눈으로 훑어 잘못 묶인 것(`파프리카`가 `파`로 갔다든지)을 찾고, `data/ingredient-overrides.json`에 수정만 적어두면 재실행 시 LLM 결과를 덮어쓴다. **수작업은 "전부 만들기"가 아니라 "틀린 것만 고치기"로 줄어든다.**

**1-d. 재료 해석기 (런타임)** — `lib/ingredients/resolve.ts` ← **AI를 쓰는 곳 (2)**

1-c는 레시피 쪽을 정리한다. 사용자가 냉장고에 직접 입력하는 쪽도 같은 정규 어휘로 들어와야 매칭이 성립한다. 사용자는 "칵테일새우"라고 칠 수도, "새우"라고 칠 수도 있다.

**4단 폴백 — 위에서 걸리면 아래로 안 내려간다:**

| 단계 | 방법 | 비용 | 커버리지 |
|---|---|---|---|
| 1 | **자동완성** — 입력 중 정규 어휘에서 후보 제시 | 0 | 대부분. 애초에 어긋난 입력을 막는 게 가장 강력한 수단 |
| 2 | **정확 일치** — 정규명 또는 이미 알려진 원문(alias)과 일치 | 0 | 1-c가 만든 매핑표 전체 |
| 3 | **부분 문자열 + 초성 + 편집거리** — 후보 1개로 좁혀질 때만 채택 | 0 | 오타, 짧은 변형 |
| 4 | **LLM 1회 해석** — "이 재료는 기존 어휘 중 무엇인가, 없으면 새 어휘" | 1회 수천분의 1달러 | 나머지 전부 |

**4단계 결과는 alias 테이블에 영구 저장한다.** 같은 표현이 두 번째로 들어오면 2단계에서 걸린다. **사전이 스스로 자란다** — 수작업 사전 관리가 없어지는 지점이 여기다.

`effort: "low"`, 입력에 정규 어휘 목록을 캐싱해 전달. UI는 결과를 확정 저장하지 않고 **"○○(으)로 등록할까요?" 확인 한 번**을 거친다 (오분류가 조용히 쌓이는 것을 막는다).

**키가 없을 때**: 1~3단계만으로 동작하고 4단계는 건너뛴다. 미해석 재료는 원문 그대로 저장되며 매칭률이 떨어질 뿐, 앱은 정상 동작한다.

**1-e. DB 적재** — `prisma/seed.ts`
`Recipe`, `RecipeIngredient`, `Ingredient`(정규명 + category + isStaple), `IngredientAlias`(원문 → Ingredient, 1-c 산출물 + 1-d 런타임 학습분), `Food`(영양성분 DB)

**검증**: `npx tsx scripts/check-matching.ts "칵테일새우,달걀,정구지"` → 새우·계란·부추 레시피가 나오는가. **일부러 별칭으로 조회해서** 정규화가 실제로 동작하는지 확인한다.

**2-b. F1 계산 모듈** — `lib/nutrition/targets.ts` (순수 함수)

명세서 §F1을 그대로 구현. 각 단계를 개별 함수로 분리해 테스트 가능하게 한다.

```
calcBMR(성별, 체중, 키, 나이)        // Mifflin-St Jeor
calcTDEE(bmr, 활동수준)              // ×1.2 / 1.375 / 1.55 / 1.725 / 1.9
calcTargetCalories(tdee, 목표, bmr)  // −500 / +0 / +400, 하한 = BMR
calcMacros(목표칼로리, 목표, 체중)    // 40:30:30 / 50:20:30 / 50:25:25
                                     // 단백질 하한 체중×1.2g, 부족분은 탄수에서 차감
```

**놓치면 안 되는 두 안전장치** (명세서가 명시적으로 요구):
- **목표 칼로리 하한 = BMR.** TDEE−500이 BMR보다 낮아지면 BMR로 올린다
- **단백질 하한 = 체중(kg)×1.2g.** 계산값이 미달이면 하한을 쓰고 부족분을 탄수화물에서 뺀다

입력 범위 검증: 나이 10~100, 키 100~250cm, 몸무게 30~300kg.

### 3단계 — 추천 점수와 제외 조건

`lib/recommend/` — 프레임워크 비의존 순수 모듈.

**3-a. F4 다음 식사 추천** — `lib/recommend/meal.ts`

```
① 잔여 칼로리  = 목표 − 오늘 누적
② 잔여 탄단지  = 목표 탄단지 − 오늘 누적 탄단지
③ 끼니 배분    = 잔여 ÷ 남은 끼니 수
                 (남은 끼니 = 추천 대상 포함, 오늘 기록 없는 끼니 수 — 위 (a) 참조)
④ 후보 추림    = 배분 칼로리 ±15% 범위의 Food
⑤ 정렬        = 잔여 탄단지 중 가장 부족한 영양소를 많이 채우는 순
```

**제외 조건 (하드 필터)**
- 기피/알레르기 재료 포함 음식 배제
- 잔여 칼로리 < 0 → 후보를 저칼로리 음식으로 한정하고 안내 메시지
- 잔여 칼로리 < 200kcal → 정식 끼니 대신 간식류로 한정

**3-b. F5 레시피 추천** — `lib/recommend/recipe.ts`

```
재료 1개 매칭 점수
   정규명 완전 일치 (새우 = 새우)                    1.0
   같은 category (닭가슴살 ↔ 닭다리살, 둘 다 "닭고기")  0.7  ← 1-c의 category가 여기서 쓰인다
   없음                                              0

매칭률 = Σ(재료별 점수) ÷ 필요 재료 수   (isStaple 재료는 분자·분모 모두에서 제외)
점수  = 매칭률
        + 유통기한 임박(3일 이내) 재료 사용 시 가산점   ← 이 앱의 핵심 가치
        − 잔여 칼로리 범위 초과 시 감점 (칼로리 조건 ON일 때만)
```

카테고리 부분 일치로 채워진 재료는 UI에서 `"닭다리살로 대체 가능"`처럼 표시한다 — 100% 매칭이라고 속이지 않는다.

**제외 조건**
- 기피/알레르기 재료 포함 레시피 배제
- 부족 재료가 임계치(기본 2개) 초과면 배제 — 단, 100% 매칭이 하나도 없으면 1~2개 부족까지 포함해 노출(명세서 F5 제약사항)

**3-c. 추천 이유 생성** — LLM 없이 템플릿으로

점수 항목이 곧 이유다. 각 항목이 왜 그 점수인지를 문자열로 함께 반환한다.
- F4: `"오늘 단백질이 142g 부족해요"` (명세서 S3)
- F5: `"유통기한이 3일 남은 두부를 씁니다. 대파만 사면 됩니다."`

**반환값**: 상위 N개 + 항목별 점수 내역 + 부족 재료 목록 + 이유 문자열.

### 7단계 — AI 추가 (선택)

재료 정규화 AI는 1단계에서 이미 들어갔다. 여기는 **없어도 v1이 성립하는** 나머지 AI다.

**7-a. F3 사진 인식** (Claude Vision, `claude-opus-5`)
- 모바일 카메라: `<input type="file" accept="image/*" capture="environment">`
- 업로드 전 클라이언트에서 긴 변 2576px로 리사이즈 (Opus 5 고해상도 상한). 사진 1장 대략 2~4센트
- **인식 결과를 1-d의 재료 해석기에 그대로 통과시킨다** — 사진에서 "칵테일새우"로 읽히든 "새우"로 읽히든 같은 정규명으로 수렴한다. 사진 인식은 "텍스트를 만들어내는 또 하나의 입력 경로"일 뿐이고, 정규화는 이미 1단계에서 풀린 문제다. 프롬프트에는 정규 어휘 목록을 함께 전달해 애초에 정규명으로 나오도록 유도한다
- **자동 저장 금지, 확인 단계 필수** (명세서 F3): 인식 결과를 체크리스트로 → 사용자가 틀린 것 해제, 누락된 것 추가 → 승인 시에만 반영 (S4 시나리오)
- 유통기한은 사진으로 알 수 없다 → 재료 카테고리별 기본 소비기한(채소 7일, 육류 3일, 냉동 90일 등)을 자동 제안하고 사용자가 수정
- 실패 경로: 키 없음 / API 오류 / 인식 불가 → 항상 수동 입력으로 폴백. 이 기능이 죽어도 F3는 온전히 동작해야 한다
- 사진 보관 정책을 정할 것 (권장: 인식 후 즉시 폐기, 서버에 남기지 않음 — 집 내부가 찍힌 사진이다)

**7-b. 추천 설명문 자연화**
3단계의 템플릿 이유를 LLM이 문장으로 다듬는다. **점수 근거를 근거로 전달**해 환각을 막는다.

**7-c. 재료 어휘 재정비 (운영)**
1-d가 런타임에 학습한 alias가 쌓이면, 주기적으로 `data/normalization-report.md`를 다시 생성해 잘못 묶인 것을 점검하고 `ingredient-overrides.json`에 반영한다. 사용자가 실제로 입력한 표현이 모이므로 시간이 갈수록 정확해진다.

## 검증 방법

**1단계 완료 시점**
```bash

npx tsx scripts/fetch-nutrients.ts      # 9.2만 건
```

```bash

```
→ F1 계산 예시 정확 재현 / F4·F5 시나리오 재현 / 하드 필터 동작.

**전체 end-to-end** (`npm run dev`)
1. `/profile`에 남 30세·175cm·75kg·보통·다이어트 → **BMR 1,699 / TDEE 2,633 / 목표 2,133**, 탄 213·단 160·지 71 표시 (S1)
2. `/log`에 아침 420kcal → 대시보드가 `420 / 2,133`, 잔여 1,713 (S2)
3. `/suggest` 점심 → 배분 약 571kcal, 단백질 부족을 이유로 고단백 음식 상위 (S3)
4. `/pantry`에 재료 5개, 두부 유통기한 3일 뒤 → 임박 표시 (S4)
   - 이때 하나는 **별칭으로 입력한다**: "칵테일새우" → 자동완성이 "새우"를 제안하거나, 확인 후 새우로 등록되는가
   - 사전에 없는 표현("정구지")을 넣어 LLM 해석 → 부추 확인 → 다시 입력했을 때 API 호출 없이 즉시 잡히는가 (자가 학습)
5. `/recipes` → 두부 계란찜 매칭률 100% 1위, 부족 재료 표시 (S5)
6. 저녁 510kcal 기록 → 합계 1,450kcal, 대시보드가 **초과가 아닌 부족**과 BMR 미달을 안내 (S5)
7. 공유 링크 생성 → 시크릿 창에서 열어 개인 정보 노출 없음 확인
8. 모바일 뷰에서 2·4번 재확인 (한 손으로 기록·재료 추가가 되는가)

## 착수 전 확인 필요

- **API 활용신청 2건** — 식약처 openapi(레시피), data.go.kr 15127578(영양성분). 승인 대기가 있을 수 있으니 0단계에서 즉시
- **알레르기/기피 재료 필드 포함 여부** — 위 (b) 참조. 최소 형태로 넣어두었으나 원치 않으면 제거
- **공공데이터 이용허락범위** — 6단계 착수 전 1회 확인
- **Claude API 키 — 1단계부터 필요** (변경됨). 재료 정규화가 AI로 옮겨졌기 때문. 1회 배치 2~3달러 + 런타임 미등록 재료 해석 시 건당 극소액.
  키가 없어도 개발은 막히지 않는다: 1-c는 정규식 파싱까지만 수행하고, 1-d는 1~3단계(자동완성·정확 일치·부분 문자열)만 동작한다. 매칭률이 떨어질 뿐 2~6단계는 그대로 진행 가능하며, 키를 넣고 `normalize-ingredients.ts`를 재실행하면 그 시점에 품질이 올라간다.
